01الشرح

1) Exceptions: ماذا يحدث عندما يفشل سطر؟

الـ Exception كائن ينشئه Python عند حدوث خطأ أثناء التنفيذ (runtime)، مثل تحويل نص غير رقمي أو القسمة على صفر أو الوصول إلى مفتاح غير موجود. عند وقوعه يتوقف التنفيذ العادي فورًا، ويصعد الاستثناء من الدالة الحالية إلى من استدعاها حتى يجد من يعالجه؛ فإن لم يجد أحدًا ينتهي البرنامج ويطبع traceback. نحتاج هذا المفهوم لأن البيانات الخارجية (إدخال المستخدم، أو مصادر البيانات عمومًا) لا يمكن ضمان صحتها مسبقًا.

لكل استثناء نوع ضمن شجرة وراثة (تذكّر درس Inheritance): BaseException ثم Exception ثم أنواع مثل ValueError وTypeError وZeroDivisionError، ويرث KeyError وIndexError من LookupError. وهذا يختلف عن SyntaxError الذي يظهر قبل بدء التنفيذ لأن الكود لا يمكن تحليله أصلًا.

القيد المهم: عالج الاستثناءات التي تتوقعها فقط؛ الخطأ البرمجي (bug) يجب أن يظهر ليُصلَح، لا أن يُخفى.

2) try و except: التقاط الفشل المتوقع

try تحيط بالكود الذي قد يفشل، وexcept تحدد ما يحدث عند فشله فلا يتوقف البرنامج. عند وقوع استثناء داخل try يُترك باقي الكتلة فورًا، ويفحص Python كتل except بالترتيب وينفذ أول كتلة يطابق نوعها نوع الاستثناء أو أحد آبائه.

استخدم as error للوصول إلى رسالة الاستثناء، ويمكنك تجميع أنواع في tuple مثل except (TypeError, ValueError). ضع الأنواع الأخص قبل الأعم، لأن النوع الأب يلتقط أبناءه ويحجب كتلة الابن بعده.

الخطأ الشائع: except: العارية تلتقط كل شيء حتى KeyboardInterrupt، وexcept Exception: على كتلة كبيرة تخفي أخطاء لم تتوقعها. حدّد النوع دائمًا.

3) else و finally: ما بعد النجاح وما يجب أن يحدث دائمًا

كتلة else تعمل فقط إذا انتهت try دون استثناء. فائدتها فصل «المحاولة الخطرة» عن «ما نفعله بنتيجتها»، فلا تلتقط except أخطاء من كود لم نقصد حمايته. أما finally فتعمل دائمًا: عند النجاح أو الفشل أو حتى عند return، وتناسب التنظيف (cleanup) مثل تحرير مورد أو إعادة حالة إلى وضعها. الترتيب: try ثم except ثم else ثم finally.

الخطأ الشائع: وضع return داخل finally يلغي أي return سابق ويبتلع الاستثناء المنتشر. لن نحتاج finally لإغلاق الملفات إلا في دروس لاحقة، أما الآن فافهمها بوصفها كتلة تنظيف مضمونة.

4) raise: ارفع الاستثناء بنفسك

عندما تكتشف أن الحالة غير صالحة (قاعدة عمل منتهكة)، فارفع استثناءً بدل أن تُرجع قيمة غامضة مثل None أو -1: raise ValueError("message"). اختر النوع الأقرب لمعنى المشكلة واكتب رسالة تشرحها. داخل except، تعيد raise وحدها رفع الاستثناء الحالي كما هو بعد تنفيذ إجراء جانبي، بينما raise NewError("...") from error تحوّله إلى نوع أنسب مع حفظ سببه الأصلي.

الخطأ الشائع: رفع Exception العام يصعّب على المستدعي التقاطه بدقة؛ وكتابة raise وحدها خارج أي except تسبب RuntimeError.

5) Exception Handling: قرارات التصميم

الـ Exception Handling ليس مجرد try/except، بل قرار: أين نعالج؟ عالج حيث تملك إجراءً مفيدًا (قيمة بديلة، إعادة محاولة، رسالة واضحة للمستخدم)، وإلا فدع الاستثناء يصعد إلى طبقة تعرف ماذا تفعل به. أسلوب Python المعتاد هو EAFP («اطلب المسامحة أسهل من الاستئذان»): جرّب ثم عالج الفشل، بدل فحص كل الشروط مسبقًا (LBYL)، لأنه أبسط ويتفادى تغيّر الحالة بين الفحص والتنفيذ.

اجعل try ضيقة (سطرًا أو سطرين)، وعالج أنواعًا محددة، ولا تكتب except ...: pass بصمت. وإن وُجدت دالة لا تحتاج استثناءً أصلًا (مثل dict.get()) فاستخدمها.

02الملخص

  • الـ Exception كائن يرفعه Python عند فشل التنفيذ؛ وإن لم يُعالج ينهي البرنامج ويطبع traceback.
  • ضع داخل try الكود الخطر فقط، والتقط أنواعًا محددة مع as error، والأخص قبل الأعم.
  • تجنّب except: العارية وexcept Exception: pass لأنهما تخفيان الأخطاء الحقيقية.
  • else لما بعد النجاح، وfinally للتنظيف وتعمل دائمًا؛ والترتيب: try ثم except ثم else ثم finally.
  • raise يرفع استثناءً عند انتهاك شرط؛ وraise وحدها داخل except تعيد الرفع، وfrom تحفظ السبب الأصلي.
  • عالج حيث تستطيع الاسترداد (EAFP)، واجعل try ضيقة، ولا تضع return داخل finally.

03أسئلة المقابلات

ماذا يحدث لو وقع Exception ولم نعالجه؟ أساسي

يصعد الاستثناء عبر سلسلة استدعاءات الدوال (call stack) بحثًا عن except مناسبة. إن لم توجد، يتوقف البرنامج ويطبع traceback يوضح نوع الاستثناء ورسالته والأسطر التي مرّ بها. وهذا ليس دائمًا سيئًا: الخطأ البرمجي غير المتوقع يفضَّل أن يظهر بوضوح بدل أن يُخفى.

متى تعمل else ومتى تعمل finally؟ أساسي

تعمل else فقط إذا انتهت try دون استثناء، وتناسب الكود الذي يعتمد على نجاح المحاولة. أما finally فتعمل دائمًا سواء نجحت العملية أو فشلت، وتناسب التنظيف.

متابعة: هل يجوز استخدام try مع finally دون except؟ نعم، فيعمل التنظيف ويستمر الاستثناء في الصعود.

لماذا تُعدّ except Exception: pass ممارسة سيئة، وما البديل؟ متوسط

لأنها تبتلع كل الأخطاء بما فيها الأخطاء البرمجية (مثل TypeError من خطأ في الكتابة)، فيستمر البرنامج ببيانات خاطئة ويصعب تتبع السبب. البديل: التقط النوع المحدد الذي تتوقعه، وعالجه فعليًا بقيمة بديلة أو رسالة واضحة، أو دعه يصعد إلى طبقة أعلى.

ما الفرق بين raise وraise error داخل كتلة except؟ متوسط

raise وحدها تعيد رفع الاستثناء الحالي كما هو دون تغيير. أما raise error فتعيد رفع الكائن نفسه لكنها تضيف سطر الرفع الحالي إلى traceback، فتكون أقل نظافة. وإذا أردت استبدال النوع مع حفظ السبب فاستخدم raise NewError("...") from error.

ماذا تطبع هذه الدالة، ولماذا؟ فخ

تطبع finally. تعمل كتلة finally قبل أن تُسلَّم قيمة return للمستدعي، ثم يحلّ return الموجود فيها محل القيمة السابقة. والأسوأ أنه لو رُفع استثناء داخل try لأُلغي وابتُلع بصمت. لذلك لا تضع return داخل finally.

04المسألة العملية

يستقبل متجر إلكتروني كميات المنتجات من نموذج طلب على شكل نصوص. اكتب دالة parse_quantity(text) تُرجع عددًا صحيحًا موجبًا أو ترفع ValueError برسالة واضحة. ثم عالج قائمة إدخالات دون أن يتوقف البرنامج عند أول إدخال خاطئ: اجمع الكميات المقبولة والرسائل المرفوضة، واحسب عدد الإدخالات المعالجة، ثم اطبع ملخصًا.

  1. فهم المطلوب

    مدخلات: قائمة نصوص مثل "3" و"abc" و"0". المطلوب: قبول الأعداد الصحيحة الموجبة فقط، وإبلاغ سبب رفض كل إدخال، ومواصلة المعالجة رغم الأخطاء.

  2. خطة الحل

    دالة واحدة تتحقق من الإدخال وترفع ValueError عند الفشل. حلقة تستدعيها داخل try مع except لجمع الأخطاء، وelse لتخزين الكمية المقبولة، وfinally لعدّ كل إدخال تمت معالجته.

  3. الكود الكامل

  4. تفسير القرارات

    حوّلنا خطأ int() الخام إلى رسالة أوضح عبر raise ... from error مع حفظ السبب الأصلي. تخزين الكمية المقبولة في else يضمن ألا تلتقط except أخطاء من append. والعدّاد في finally يُحدَّث دائمًا، نجح الإدخال أو فشل. والمعالجة تلتقط ValueError فقط لأنه الفشل المتوقع.

  5. اختبار سريع

    جرّب parse_quantity(" 5 ") فتحصل على 5 لأن int() يتجاهل المسافات الجانبية، وجرّب "2.5" و"-4" فيُرفض الأول لأنه ليس عددًا صحيحًا ويُرفض الثاني لأنه غير موجب. وأضف إدخالًا من نوع None لترى TypeError غير الملتقط، وهو سلوك مقصود يكشف خطأ برمجيًا لا خطأ إدخال.

  6. تحسين أو بديل

    بديل LBYL هو text.isdigit()، لكنه يرفض "-3" ويقبل رموزًا غير ASCII مثل "²" ثم يفشل لاحقًا في int()، لذلك تبقى المحاولة مع الاستثناء أدق. ويمكن لاحقًا تحسين الرسائل بإرجاع بيانات منظمة بدل نصوص.
